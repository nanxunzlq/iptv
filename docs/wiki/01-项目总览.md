# 01 · 项目总览

## 1. 定位与目标

[`nanxunzlq/iptv`](../../README.md) 是一个**个人 IPTV 直播源与配套工具聚合仓库**，目标有三个：

1. **可用**：提供在河南移动宽带环境下实测可播的 283 条直播源（m3u + DIYP txt 双格式）。
2. **可复现**：把"采集 → 测速 → 生成 → 校验"的工具链固化在仓库内，源失效时可自行重采。
3. **可维护**：用 GitHub Actions 自动校验文件一致性、README 声明与订阅地址可达性，避免"改了数据忘了改文档"。

它**不是**一个单一应用：仓库里同时存在数据文件、一个 Node.js CLI、一个 Python 全栈系统（含 GUI、Web 服务、推流），三者独立运行、通过文件产物衔接。

### 明确的非目标

- 不镜像 [iptv-org/iptv](https://github.com/iptv-org/iptv)（约 1.3 GB，上游已有成熟维护）。
- 不提供"通用全球源"：只维护河南移动这一套源。
- 不在 CI 中实测运营商直播源（runner 到内网源必然不通，见 [08](./08-质量保障与维护.md)）。

## 3. 技术栈

### 3.1 数据层

- 纯文本：M3U（`#EXTINF` / `#EXTVLCOPT`）与 DIYP（`#genre#`）。
- 无数据库、无构建步骤；Git 即版本管理。

### 3.2 iptv-checker（Node.js）

| 维度 | 选型 |
|---|---|
| 运行时 | Node.js `>=22.12.0`，ESM（`"type": "module"`） |
| CLI | `commander` + `progress` + `colors` + `get-stdin` |
| 网络 | `axios` + `axios-retry` + `socks-proxy-agent` + `https.Agent` |
| 解析 | `iptv-playlist-parser`、`valid-url`、`normalize-url` |
| 媒体探测 | 外部 `ffprobe`（FFmpeg），`child_process.exec` |
| 并发 | `async.eachLimit`，默认并发 = CPU 核数 |
| 测试 | `jest` + `babel-jest` + `msw`（Mock Service Worker） |

详见 [package.json](../../tools/iptv-checker/package.json#L34-L57)。

### 3.3 iptv-api（Python 3.14）

| 维度 | 选型 |
|---|---|
| 运行时 | Python 3.14，`asyncio` + `aiohttp` |
| 配置 | `configparser` + 自定义校验规则 |
| Web 服务 | Flask 3.1 + gunicorn（容器） / Flask dev（本地） |
| 桌面 GUI | PySide6 6.11 + `qfluentwidgets` + `pysidesix-frameless-window` |
| 媒体探测 | FFmpeg / ffprobe 子进程 |
| 推流 | nginx-rtmp + FFmpeg（HLS → RTMP） |
| 持久化 | SQLite（WAL，含回滚日志降级）+ gzip/pickle 缓存 |
| 国际化 | `locales/zh_CN.json`、`locales/en.json` |
| 打包 | PyInstaller（`desktop_ui.spec` / `tkinter_ui.spec`） |

详见 [Pipfile](../../tools/iptv-api/Pipfile) 与 [Dockerfile](../../tools/iptv-api/Dockerfile)。

## 4. 运行时形态一览

iptv-api 一个代码库支持 **5 种运行形态**，入口与差异如下：

| 形态 | 启动命令 | 入口 | 是否需要 GUI | 典型场景 |
|---|---|---|---|---|
| 命令行（单次） | `pipenv run dev` | [main.py](../../tools/iptv-api/main.py#L972-L989) | 否 | 本地调试、脚本 |
| 常驻调度 | 同上（`update_interval > 0`） | `UpdateSource.start()` → `scheduler()` | 否 | 服务器定时更新 |
| Web 服务 | `pipenv run service` | [service/app.py](../../tools/iptv-api/service/app.py#L511) | 否 | 提供结果订阅地址 |
| 桌面 GUI | `pipenv run ui` | [desktop_ui/app.py](../../tools/iptv-api/desktop_ui/app.py#L66-L115) | 是 | Windows / macOS 日常使用 |
| Docker | `docker compose up -d` | [entrypoint.sh](../../tools/iptv-api/entrypoint.sh) | 否 | NAS / 长期部署 |

GUI 与 Web 服务的关系：GUI 可内嵌启动一个 **子进程 Web 服务**（`--service` 参数），并通过 `--parent-pid` 监控父进程退出，父进程结束后自动清理推流与 nginx（[app.py](../../tools/iptv-api/service/app.py#L95-L117)）。

## 5. 数据规模与实测结论

- **频道数**：283 条（m3u / txt 一致）。
- **分组数**：14。
- **实测（2026-10-20，本机河南移动宽带）**：低速率单遍探测下 283 条全部可播；280 条直出 HLS 清单，3 条首次跳转、复验返回 206。
- **重要方法论**：运营商 CDN 对高频请求会短暂返回 `404`，**不是真失效**。高并发探测（如 12 并发 × 6 采样）会误判；建议 `iptv-checker -p 1`，且"判失效前务必冷却复验"。
- **跨运营商对照（2026-10-23）**：移动 132 个唯一频道逐一匹配河南电信源（58 条），命中 54、缺口 78、电信独有 5；电信源本身 57/58 可播。详见 [`河南移动-河南电信频道对照.md`](../河南移动-河南电信频道对照.md)。

以上结论来自 [README 二、河南移动直播源](../../README.md#直播源与频道构成) 与 `docs/iptv-频道探活明细-*.json`（工作区分析产物，非仓库内文件）。

## 6. 项目历史与边界

- 2026-09-16 由原 5 个独立仓库合并而来，部分组件后续移除；`docs/ecosystem.md` 由原 `iptv-org` 仓库 README 整理。
- 许可证不是单一的：
  - `河南移动/`、根目录自有文件 → **MIT**；
  - `tools/iptv-checker/` → **MIT**（保留上游版权）；
  - `tools/iptv-api/` → **AGPL-3.0**（强 copyleft）。
- `iptv-api` 之所以用 submodule 而非直接并入，是为了避免 AGPL 的"组合作品"认定导致整个仓库被迫 AGPL 化，详见 [THIRD-PARTY.md](../../THIRD-PARTY.md#L41-L45)。
