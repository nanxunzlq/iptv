# 08 · 质量保障与维护

本仓库没有传统意义的"测试金字塔"，质量保障分布在三个不同层面：**数据一致性（CI）**、**工具正确性（单元测试）**、**依赖与发布（机器人 + 工作流）**。本章按层说明"守门人是谁、失败会怎样、维护者该怎么做"。

---

## 一、三层保障总览

| 层 | 对象 | 手段 | 失败表现 |
|---|---|---|---|
| 数据层 | `河南移动/*.m3u` / `*.txt` | [iptv-health-check.yml](../../.github/workflows/iptv-health-check.yml) + [等价性脚本](../../.github/scripts/check_playlist_equivalence.py) | 工作流红 + `[自动巡检]` Issue |
| 工具层 | iptv-checker / iptv-api | Jest / `unittest` | 测试工作流红，阻止发布 |
| 依赖层 | npm / submodule / actions | Dependabot | 提出 PR，人工评审 |

## 二、主仓库自检

### 2.1 触发条件

| 触发 | 条件 |
|---|---|
| 定时 | 每周一 `03:17 UTC`（避开整点高峰） |
| 推送 | `河南移动/**`、`README.md`、workflow 自身、`.github/scripts/**` |
| 手动 | `workflow_dispatch`，可选 `probe_streams` |

并发组为 `repo-self-check`，`cancel-in-progress: false`：新运行不会打断进行中的自检。

### 2.2 检查项

| # | 检查 | 判定 |
|---|---|---|
| 1 | 频道数一致性 | m3u `#EXTINF` 数、txt `频道名,URL` 数，都必须等于 README 声明值 |
| 2 | 结构完整性 | 每个 `#EXTINF` 后必须有 URL；URL 不得重复；首行 `#EXTM3U`；txt 含 `#genre#` |
| 3 | 分组质量 | 每个频道必须有 `group-title`；m3u 不得出现 `#genre#`；分组名不得含逗号 |
| 4 | 分类数量一致 | README 的 14 个分类数量与 m3u 实际 `group-title` 计数一致 |
| 5 | m3u ↔ txt 等价 | 频道名集合、URL 集合、`频道名 → URL` 映射完全一致（顺序不限） |
| 6 | 订阅可达 | 两个 Raw 地址返回 HTTP 200 |

任一项失败即整体失败，`::error::` 注解会直接标在 workflow 日志与 PR 检查中。

### 2.3 等价性脚本的工作方式

[check_playlist_equivalence.py](../../.github/scripts/check_playlist_equivalence.py) 只有约 100 行，逻辑刻意保持简单：

```python
M3U_ENTRY = re.compile(r"^#EXTINF[^\r\n]*?,(.*?)\r?\n(https?://\S+)", re.M)
```

1. `parse_m3u`：用正则一次性取出 `(显示名, URL)`；
2. `parse_txt`：跳过 `#genre#` 与空行，按首个逗号切分；
3. 比较三组结果：频道名集合、URL 集合、`name → url` 映射；
4. 差异逐条打印并退出码 1；通过时用 `GITHUB_STEP_SUMMARY` 输出摘要。

> 只比较"名字/URL/映射"，不强制顺序：两版文件允许按不同顺序排列，方便人工维护。

### 2.4 为什么 CI 不做日常探活

河南移动源是运营商宽带内网服务，GitHub runner 上**必然全红**。把探活放进每日 CI 只会产生噪音。因此：

- 日常只校验**文件层面**的一致性；
- 实测被设计为手动开关 `probe_streams`，且 README 明确提示结果仅供参考；
- 真正的探活应在本地宽带环境用 `iptv-checker -p 1` 执行。

### 2.5 失败通知的防刷屏

`notify` job 使用固定标题 `[自动巡检]`：

1. 搜索仓库内是否已存在带该标记的 open Issue；
2. 存在则**更新正文**（追加本次失败项与运行链接），不新建；
3. 不存在才创建。

因此连续失败只会在一条 Issue 上累积，不会刷满通知。

## 三、`iptv-checker` 测试

| 项 | 值 |
|---|---|
| 框架 | Jest 29 + babel-jest（ESM 需 `--experimental-vm-modules`） |
| 用例数 | 16（全部通过） |
| 覆盖重点 | PlaylistTester / StreamTester / StreamLoader / FFprobe 输出与错误解析 / Playlist 追加 / HTTP 错误分类 |

**已知环境坑**：系统代理会让 axios + msw 组合产生畸形请求，导致假失败。运行前剥离代理：

```bash
env -u http_proxy -u https_proxy npm test
```

Windows PowerShell：

```powershell
Remove-Item Env:http_proxy, Env:https_proxy -ErrorAction SilentlyContinue
npm test
```

### 4.2 本地运行

```bash
cd tools/iptv-api
pipenv install --dev
pipenv run python -m unittest discover -s tests -v
```

### 4.3 `tests.yml`

[工作流](../../tools/iptv-api/.github/workflows/tests.yml) 步骤：

1. `actions/checkout`；
2. Python **3.14** + pipenv 缓存；
3. 安装 Qt 运行库 `libegl1`（GUI 测试需要），并设 `QT_QPA_PLATFORM=offscreen` 无头运行；
4. `pipenv sync --dev`（严格按 lock 安装）；
5. `pipenv verify`（校验 lock 与 Pipfile 一致）；
6. `unittest discover -s tests -v`；
7. `compileall` 编译 `main.py service updates utils desktop_ui tests`，捕获语法错误。

该工作流既可被其他工作流 `workflow_call` 复用，也可手动触发。

### 4.4 其他工作流

| 工作流 | 作用 |
|---|---|
| `main.yml` | `Generate playlist manually`：手动生成 + Pages 发布 |
| `tests.yml` | 单元测试 + 编译检查 |
| `validate-pr.yml` | 自动关闭无效 PR：无提交、未勾选贡献确认、非可信成员修改 `config/` 或 `output/` |

## 五、依赖维护

### 5.1 Dependabot 策略

| 生态 | 目录 | 频率 | 提交前缀 | 限制 |
|---|---|---|---|---|
| npm | `/tools/iptv-checker` | 每周一 03:40（Asia/Shanghai） | `chore(deps)` | 最多 3 个 PR；dev/prod 的 minor+patch 分组；**忽略 semver-major** |
| gitsubmodule | `/` | 每周一 03:50 | `chore(submodule)` | 最多 2 个 PR |
| github-actions | `/` | 每月 | `chore(ci)` | 最多 2 个 PR |

忽略主版本的原因写在配置注释里：工具目录是上游快照，改 `package.json` 声明范围会与上游源码产生分歧；安全更新走独立通道，不受 ignore 影响。

### 5.2 已知依赖风险

| 项 | 状态 | 影响 |
|---|---|---|
| `sprintf-js`（中危） | Dependabot 开放中 | 仅 jest/babel 开发链路 |
| `braces`（高危） | 上游无修复版本，已忽略 | 仅开发链路 |
| `npm audit` 33 条 | 均为上述两者的路径级计数 | **不影响 CLI 运行时** |
| `iptv-checker` 上游停更 | 0.30.3 为最终版 | 安全问题只能改本地锁文件 |
| Python 3.14 | 较新版本，依赖全部 `==` 锁定 | 升级需整体验证 |

## 六、数据更新维护手册

修改 `河南移动/` 下的源时，按以下顺序操作：

```text
1. 采集/获取新源
      ↓
2. 本地探活（低并发、冷却复验）
   npx iptv-checker -p 1 -r 1 ./候选.m3u
      ↓
3. 人工复核 online.m3u / failed.m3u
      ↓
4. 同时更新 河南移动.m3u 与 河南移动.txt（频道名/URL/分组保持一致）
      ↓
5. 更新 README 中的总条数与 14 个分类计数
      ↓
6. 本地跑等价性脚本
   python .github/scripts/check_playlist_equivalence.py
      ↓
7. 提交（Conventional Commits，如 docs: 更新频道）
      ↓
8. CI 自检全绿
```

**硬性规则**

- 两版文件必须**同时**修改，不允许只改一份；
- 频道名/URL/分组三者必须一一对应；
- 备用线路命名保持 `·备用线路N` 后缀；
- `group-title` 不得含逗号，m3u 中不得出现 `#genre#`；
- README 的数量表是 CI 的输入，改数据必须同步改 README。

**提交信息规范**：Conventional Commits（`feat:`、`fix:`、`docs:`、`chore(deps):`、`chore(submodule):`、`chore(ci):`）。

## 七、排障与运行证据

iptv-api 把"这次运行发生了什么"沉淀成可查询的证据，排障时按序查看：

| 证据 | 位置 | 用途 |
|---|---|---|
| 运行状态 | `output/data/run_state.json` | 最后状态（`running/completed/completed_empty/cancelled/failed`）与原因 |
| 文本日志 | `output/log/log.log` | 带时间、级别、运行 ID 的主日志 |
| 结构化事件 | `output/log/runtime.jsonl` | 机器可读，按 `event` / `phase` 过滤 |
| 测速明细 | `output/log/speed_test.jsonl` | 每个接口的速率/延迟/失败类型 |
| 未匹配频道 | `output/log/unmatch.log` | 模板里有、源里找不到的频道 |
| 频道状态库 | `output/data/channel_results.db` | 频道健康度、候选池、历史测量、导出快照 |

GUI 的"频道/日志/任务历史"页面读的就是上述数据，不另建一套状态。

## 八、风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 运营商源策略调整 | 大面积失效 | 本地探活复核后重新采集；README 已声明 |
| 高频探活误判 | 误删正常源 | 低并发 + 冷却复验；CI 不自动探活 |
| `iptv-checker` 上游停更 | 无官方修复 | 锁文件内更新；不改上游源码 |
| AGPL 传染 | 许可证风险 | submodule 隔离；对外提供服务时履行 AGPL |
| submodule 未初始化 | 目录为空、命令失败 | 文档提供两种初始化方式 |
| 网络盘 SQLite WAL 失败 | `disk I/O error` | 自动降级 DELETE journal |
| Python 3.14 生态 | 依赖兼容问题 | Pipfile.lock 全量锁定 + CI `pipenv verify` |
